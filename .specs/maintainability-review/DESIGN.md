# Maintainability review — устройство

Статус: **проектирование**. Ничего не реализовано.

## Поток

```
staged snapshot (кандидаты — из изменённых путей, поддержка — по всему снимку)
        │
        ▼
[1] Извлечение сигнатур (детерминированно, без модели)
    адаптер JS/TS: @babel/parser
    адаптер Python: stdlib ast, если интерпретатор доступен
    иной язык → статус unsupported для его путей
        │
        ▼
[2] Группировка (детерминированно)
    максимальные частые наборы параметров, порог и размер из конфигурации
        │
        ▼  .review/maintainability.json  (maintainability@1)
[3] review-maintainability (отдельный подагент, model: "@task")
    план → чтение конкретных мест → наблюдение → рефлексия → решение
        │
        ▼
[4] review-finding-verifier (существующая независимая проверка)
    проверяет и пункты сопровождения, и кандидатов дефектов отдельно
        │
        ▼
[5] Синтез: ### Maintainability + ### Notes, вердикт по существующим правилам
    и два новых: нет результата запланированной стадии → BLOCK;
    policy = block и есть блокирующий пункт → BLOCK
```

## Схема данных `maintainability@1`

```json
{
  "schema": "maintainability@1",
  "diffHash": "sha256 staged binary diff",
  "status": "analyzed | no-candidates | unsupported | failed",
  "coverage": "full | partial",
  "scan": { "filesRead": 84, "filesSkipped": 1, "elapsedMs": 168, "truncated": false },
  "config": { "minSupport": 4, "minSize": 2, "maxGroupSize": 4, "maxSignatureParams": 8, "maxGroups": 10, "maxCandidates": 5, "maxFileBytes": 524288, "maxScanFiles": 4000, "maxScanMs": 5000, "policy": "block" },
  "languages": [
    { "language": "javascript", "parser": "@babel/parser", "filesParsed": 3, "filesFailed": 0 }
  ],
  "unparsedFiles": [ { "path": "src/x.ts", "reason": "syntax | unsupported-syntax | too-large | unreadable | no-interpreter | unavailable-parser" } ],
  "failures": [ { "path": "src/x.mjs", "reason": "infrastructure", "message": "..." } ],
  "excluded": [ { "path": "tests/x.test.mjs", "ground": "test-class" } ],
  "groups": [
    {
      "groupId": "g1",
      "params": ["sessionId", "runRoot", "attemptId"],
      "support": 14,
      "supportComplete": true,
      "stagedTouchCount": 6,
      "occurrences": [
        { "path": "src/a.mjs", "lineStart": 12, "lineEnd": 12, "inStagedDiff": true, "role": "definition | forwarder | call-site" }
      ]
    }
  ]
}
```

Поля `support`, `supportComplete` и `stagedTouchCount` вычисляет код. Подагент их только читает: если он называет другое число, это расхождение, а не новый факт.

`support` считается по всему staged-снимку (MR-01). Ограничивать подсчёт изменёнными путями нельзя: группа из шестнадцати узлов при изменении двух из них не прошла бы порог и осталась бы невидимой. Поле `inStagedDiff` при этом осмысленно — оно отмечает вхождения, попавшие в изменение, и `stagedTouchCount` считается по нему. Скан ограничен `maxFileBytes`, `maxScanFiles` и `maxScanMs` (MR-13); при усечении `supportComplete` равен `false`, и `support` читается как «не менее N».

## Ответ подагента

```json
{
  "language_coverage": [ { "language": "javascript", "status": "analyzed" } ],
  "planned_checks": [
    { "candidate_id": "maintainability-1", "question": "одна ли это сущность", "confirm_if": "...", "refute_if": "..." }
  ],
  "observed": [ { "candidate_id": "maintainability-1", "path": "src/a.mjs", "line_start": 12, "line_end": 40 } ],
  "candidates": [
    {
      "candidate_id": "maintainability-1",
      "group_id": "g1",
      "params": ["sessionId", "runRoot", "attemptId"],
      "decision": "confirmed | rejected | not_proven",
      "meaning": "что именно описывает группа",
      "coordinated_change": "конкретное изменение, требующее правок в перечисленных местах",
      "forwarding_only": true,
      "reflection": "сильнейший контраргумент с ссылкой path:line и итоговое решение",
      "counterargument": "сильнейший аргумент против",
      "counterargument_evidence": ["src/b.mjs:31"],
      "impact": "цена сопровождения или причина, почему её нет",
      "stated_cost": "названное согласованное изменение и места правок; пустая строка, если цены нет",
      "priority": "P1 | P2",
      "evidence": ["src/a.mjs:12", "src/b.mjs:31"],
      "triage_ground": "framework-signature | generated-code | unrelated-names | varying-subset | stated-cost | no-stated-cost"
    }
  ],
  "budget": { "candidates_seen": 14, "candidates_analyzed": 5, "tool_calls_used": 18, "stopped_reason": "analyzed-all | budget | no-candidates" },
  "unproven_items": [ { "candidate_id": "maintainability-6", "reason": "budget" } ]
}
```

`planned_checks` и `reflection` — не скрытые рассуждения, а проверяемые артефакты: вопрос, условие подтверждения, условие опровержения, прочитанные места. Рефлексия без ссылки `path:line` не считается выполненной.

Пункт блокирует коммит только при одновременном `decision: confirmed`, непустом `stated_cost`, `priority: P2` и `forwarding_only: false`. Поля `stated_cost` и `priority` обязательны в схеме: без них критерии приёмки требуют значений, которых в ответе негде записать.

## Что меняется в проверке вердикта

Проверка вердикта сегодня знает три имени стадий и не получает списка запланированных стадий. Поэтому оба обещания — блокировка по политике и отказ на пропавшей стадии — без её изменения невыполнимы при любом ответе подагента. Изменение названо здесь поимённо, чтобы фаза T5 не свелась к «добавить агента и текст».

- `src/native/verdict.mjs`: новая константа `MAINTAINABILITY_AGENT = 'review-maintainability'`; `evaluateReview` получает два дополнительных входа — `planned` (имена запланированных стадий) и `maintainability` (`{ policy, status, coverage, candidates }`).
- Новые правила `PASS`: если `planned` содержит имя стадии, обязан существовать завершённый этап с этим агентом и валидной схемой; при `policy === 'block'` не должно быть ни одного блокирующего пункта (четыре поля выше); при `status === 'failed'` и политике не `off` — `BLOCK`.
- Пункты сопровождения не попадают в `confirmed_findings` и `confirmed_coverage_gaps`: вердикт читает `confirmed_maintainability`. Существующие ветви `PASS` и существующие проверки не меняются, новые проверки добавляются рядом.
- `agents/reviewer-kit.md`: имя подагента добавляется в `spawns`; без этого OMP не даст его запустить, и стадия будет «запланирована и отсутствует» на каждом коммите.
- `src/native/assignment.mjs`: задание получает путь к файлу кандидатов и хеш изменения; иначе подагент не знает, где список, и начинает искать его сам.
- `scripts/check-layout.mjs`: новые файлы (адаптеры, агент, скрипт измерений) входят в обязательный список, иначе поставка может уехать без них при зелёном `npm run check`.

## Решения

### D-1. Разбор синтаксиса вместо поиска по тексту

**Решение:** разбирать синтаксическое дерево; JS/TS через `@babel/parser`, Python через stdlib `ast`. Оба адаптера входят в первую поставку (решение владельца 2026-11-01), пакет `@babel/parser` объявляется прямой зависимостью.
**Причина:** параметры нужно отличать от одноимённых переменных, комментариев и строк. Текстовый поиск даёт неуправляемый шум и не отделяет объявления от вызовов.
**Компромисс:** требует зависимости для JS/TS; для остальных языков нужен отдельный адаптер или честный статус `unsupported`.
**Альтернативы:** `ast-grep` — на этой машине файла в PATH нет, дочерний процесс его не запускает (команда доступна только внутри сессии), поэтому как зависимость без установки не годится; Semgrep Community не выполняет межфайловый анализ и не решает задачу агрегата «одни и те же параметры в N функциях».

### D-2. Отдельный подагент, а не новая полоса существующего охотника

**Решение:** `review-maintainability` — сосед охотников, до верификатора.
**Причина:** действующий охотник прямо запрещает структурные замечания к функционально корректному коду и не имеет цикла план/действие/рефлексия. Расширение его полномочий смешало бы два несовместимых правила шума.
**Компромисс:** ещё одна стадия и ещё один участник; стоимость ограничивается тем, что стадия планируется только при наличии кандидатов.

### D-3. Максимальные группы, а не все подмножества

**Решение:** отбрасывать подмножества групп с не меньшей поддержкой; порог и размер из конфигурации.
**Причина:** замер: 5 973 группы из 1 221 сигнатуры при перечислении всех подмножеств, и верхняя группа — `monkeypatch, tmp_path` в 270 функциях. Такой отчёт непригоден ни человеку, ни модели, а верхняя строка подтверждает, что тестовый код обязан исключаться.
**Компромисс:** максимальная группа может быть шире реальной сущности; смысловую проверку выполняет подагент, а не порог.

### D-4. Блокировка по умолчанию с доказанной ценой (решение владельца 2026-11-01)

**Решение:** по умолчанию `block`; блокируется только подтверждённый пункт, называющий конкретное согласованное изменение и места правок, с приоритетом `P2`. Пункт без такой цены остаётся рекомендацией в `### Notes`. Режимы `advisory` и `off` доступны явной переменной. Решение принимает код по четырём машинным полям (`decision`, `stated_cost`, `priority`, `forwarding_only`), а не формулировка в отчёте; чистая пересылка набора цены не создаёт.
**Причина:** владелец выбрал вариант, при котором проблема сопровождения останавливает коммит, но только при доказанной цене; это удерживает границу против вкусовщины.
**Компромисс:** ошибка в оценке цены останавливает коммит; поэтому цена обязана быть проверяемой (§ «Критерии WHEN/IF», AT-13), а порог по умолчанию — консервативным (поддержка ≥ 4).

### D-5. Тестовый код — стенд, а не продукт

**Решение:** файлы класса `test` не дают кандидатов и не повышают поддержку.
**Причина:** замер показывает, что верхние группы в тестах — это `monkeypatch, tmp_path` из фикстур; включение тестов гарантированно даёт шум.
**Компромисс:** повторение в тестах не отслеживается вообще; это записывается в отчёт.

### D-6. Отказ инфраструктуры — не «чисто»

**Решение:** запланированная стадия, завершившаяся ошибкой, даёт `BLOCK`; проверка вердикта получает список запланированных стадий и отклоняет `PASS`, если запланированная стадия вообще не дала результата.
**Причина:** молчаливый пропуск создаёт ложную уверенность, что проверка выполнялась.
**Компромисс:** инфраструктурные сбои останавливают коммит; отключение возможно только явной политикой `off` с записью в отчёте.

### D-7. Никакого цикла автоисправлений

**Решение:** подагент только читает и рекомендует.
**Причина:** автоматическое объединение параметров меняет публичные сигнатуры и требует отдельного решения; в ревью это недопустимо.

## Отчёт

- `### Maintainability`: подтверждённые пункты — группа параметров, места вхождений, названная цена сопровождения, ссылки на доказательства.
- `### Notes`: исключения (`test-class`, неподдержанный язык, ошибки разбора), бюджетные `not_proven`, отклонённые кандидаты с основанием.
- `### Verified-OK`: что именно прочитано по каждому подтверждённому и отклонённому кандидату.

## Стоимость

Детерминированная часть: 2–4 мс на файл (JS/TS, повторные прогоны; первый прогон включает загрузку парсера — 353 мс на 84 файла) и 3,3 мс на файл (Python). Изменение в десяток файлов стоит десятки миллисекунд, подсчёт поддержки по всему снимку — сотни, отсюда предел `maxScanMs` = 5 000 (MR-13). Подагент: до 5 кандидатов и до 20 вызовов инструментов, чтение только по местам вхождений. Числа воспроизводятся командой `node scripts/measure-maintainability.mjs` из T1.

# Maintainability review — план работ

Статус: **план для нереализованного расширения**. Порядок фаз обязателен: каждая следующая опирается на доказательства предыдущей.

## T1. Извлечение сигнатур из staged-снимка

- Добавить `src/native/maintainability/extract.mjs`: адаптер JS/TS (`@babel/parser`) и адаптер Python (stdlib `ast`). Оба адаптера обязательны в первой поставке; отсутствие интерпретатора Python даёт `no-interpreter` для python-путей.
- Применить пределы MR-13 до чтения файла: `maxFileBytes`, `maxScanFiles`, `maxScanMs`; превышение любого пишет `unparsed` с причиной и ставит `coverage: partial`, но не меняет статус на `failed`.
- Добавить `scripts/measure-maintainability.mjs`: воспроизводит числа из таблицы замеров (разбор JS/TS, разбор Python, наивная группировка) на указанном дереве и печатает время, число файлов и групп. Без него числа в REQUIREMENTS невоспроизводимы.
- `@babel/parser` объявить прямой зависимостью в `package.json` (решение владельца 2026-11-01) и обновить `bun.lock`.
- Кандидаты отбирать по путям изменения, а поддержку считать по всему staged-снимку (MR-01): иначе группа из 16 узлов при изменении 2 из них не пройдёт порог. Из рабочего дерева не читать ничего.
- Различать объявление, пересылку и вызов: для пересылки нужен признак `forwarder`, и он обязан доехать до `forwarding_only` в ответе подагента — от этого зависит право блокировать (MR-08).
- Done When: на fixture из трёх файлов разных языков извлекаются параметры с точными строками; файл с декораторами и файл сверх `maxFileBytes` попадают в `unparsedFiles` с причиной и не меняют статус на `failed`; fixture «16 мест, изменение трогает 2» даёт `support: 16`; повторный запуск даёт побайтно тот же результат; `node scripts/measure-maintainability.mjs` печатает числа, совпадающие с таблицей замеров.

## T2. Группировка и пороги

- `group-clumps.mjs`: максимальные частые наборы, исключение `self`/`cls`/`*args`/`**kwargs`.
- Исключение файлов класса `test` и сгенерированных путей по детерминированным правилам; каждое исключение — запись с путём и основанием.
- Done When: fixture с подмножествами даёт только максимальную группу; порог и размер печатаются в отчёте; тестовый файл не повышает поддержку (проверяется сравнением с/без него).

## T3. Файл результата и статусы

- Записать `.review/maintainability.json` по схеме `maintainability@1` рядом с `diff.patch`, до удаления снимка; файл нужен и при `coverage: partial`.
- Реализовать четыре статуса, `coverage`, `scan` и `unparsedFiles`; `no-candidates` невозможен при непустом `failures` (статус `failed`), а `unparsedFiles` даёт `coverage: partial` без смены статуса.
- Done When: четыре fixture дают четыре разных статуса; содержимое файла сверяется со схемой в проверке.

## T4. Подагент `review-maintainability`

- `agents/review-maintainability.md`: `model: "@task"`, инструменты только для чтения, схема ответа из [DESIGN.md](DESIGN.md).
- Текст задания: план по кандидатам, чтение мест вхождений, контраргумент, решение со ссылками.
- Done When: определение содержит обязательные поля схемы; ответ без `reflection`/`planned_checks` отклоняется проверкой контракта; `task` отсутствует в инструментах.

## T5. Стадия в оркестраторе и вердикт

- В `agents/reviewer-kit.md` добавить стадию после охотников и до верификатора **и вписать имя подагента в `spawns`** — без этого OMP не даст его запустить.
- В `src/native/assignment.mjs` передать подагенту путь к `maintainability.json` и `diffHash`; иначе стадия начинается с поиска собственных входов.
- В `src/native/verdict.mjs`: константа `MAINTAINABILITY_AGENT`, новые входы `planned` и `maintainability`, правило «запланированная стадия не дала результата → `BLOCK`», правило «`policy = block` и есть блокирующий пункт → `BLOCK`», `status = failed` при политике не `off` → `BLOCK`. Пункты сопровождения читаются из `confirmed_maintainability` и в существующие блокирующие поля не попадают.
- Внести новые файлы в обязательный список `scripts/check-layout.mjs`: `agents/review-maintainability.md`, адаптеры, `scripts/measure-maintainability.mjs`.
- Done When: сценарии «кандидатов нет → стадия не запускалась и это видно», «кандидаты есть → стадия завершена», «стадия упала → BLOCK», «стадия запланирована и отсутствует → BLOCK даже при отчёте, который утверждает успех» проходят на реальных формах результатов, а не на моках.

## T6. Отчёт и политика

- Разделы `### Maintainability` и `### Notes`; политика `OMP_REVIEW_KIT_MAINTAINABILITY` (`off`|`advisory`|`block`), по умолчанию `block`.
- Done When: по умолчанию блокирует только пункт с названной ценой сопровождения, пункт без цены остаётся в заметках; при явном `advisory` вердикт не меняется; при `off` в отчёте есть строка об отключении.

## T7. Проверки

- Модульные проверки по матрице [ACCEPTANCE_CRITERIA.md](ACCEPTANCE_CRITERIA.md); проверка реального Git-хука с подготовленным staged-изменением.

- Done When: весь существующий набор kit зелёный без ослабления утверждений; новые проверки падают при откате соответствующего поведения; `npm run check` и мутационный гейт зелёные.

## T8. Документация и релиз

- Обновить `AGENTS.md`, `CHANGELOG.md`, `ROADMAP.md` и записать в них прямую зависимость `@babel/parser`, охват JS/TS и Python, политику блокировки по умолчанию, новые входы проверки вердикта и обязательность записи имени подагента в `spawns`.
- Done When: документация называет фактическое поведение и границы (включая `unsupported`-языки), а не намерения.

## 1. Проблема: «Ловушка синтаксической корректности»

### 1.1. Анатомия декомпозиционного сбоя LLM-агентов
Когда ИИ-агенту поручают нетривиальную инженерную задачу или составление дорожной карты реализации (roadmap), модель часто испытывает «страх прямого изменения доменного ядра». Вместо реализации прикладной логики модель смещается в **мета-проектирование инфраструктуры контроля**.

Возникает **паразитная надстройка** — самоподдерживающаяся система ритуалов, скриптов и обёрток:
1. **Взрыв точек входа (Entrypoint Explosion):** Дробление логики на десятки микро-CLI вместо методов доменных сервисов.
2. **Несоразмерная безопасность (Disproportionate Security):** Внедрение асимметричной криптографии (Ed25519), цепочек доверия и валидации ключей для локальных однопользовательских операций.
3. **Параллельный самодельный транспорт (Shadow Transport):** Изобретение файлового IPC через папки `inbox` и коды возврата процесса при наличии готовой шины событий или механизмов прерываний во фреймворке.
4. **Валидация ритуала вместо валидации продукта (Process vs Product Validation):** Построение систем квитанций (`TaskProofBody`), проверяющих, как модель писала код (снимки stdout/stderr, хэши промежуточных шагов), вместо проверки наблюдаемого бизнес-поведения.
5. **Паразитный перехват (Telemetry Hoarding):** Обёртки над стандартными системными вызовами (`capture-command`) для сохранения каждого бинарного байта вывода в базу ради бюрократических доказательств запуска.

### 1.2. Почему текущий ревью-конвейер v0.2.0 пропускает этот код
В существующих стандартах многостадийного ревью (PR-Agent, Sashiko, а также `skills/multi-stage-review/SKILL.md`) закреплены жесткие **анти-шумовые запреты**:
- *«Never suggest architectural or design pattern refactorings if current code is correct.»*
- *«Never speculate on potential breakage without citing a concrete, reachable callsite.»*
- *«Never report advice without a concrete failing trigger scenario.»*

Эти правила создавались для защиты от придирок человека-ревьюера к стилю и именованию. Но в эпоху автономных ИИ-агентов они создают **брешь в безопасности кодовой базы**:
- 41 CLI-скрипт компилируются и не падают с синтаксической ошибкой.
- Модуль Ed25519 корректно подписывает и проверяет байты.
- Файловый IPC по коду 20 технически записывает JSON на диск.
- Валидатор квитанций успешно проверяет 28 файлов.

**Парадокс:** код на 100% синтаксически корректен, не содержит разыменований null-указателей и проходит текущий `lane: "correctness"`. Любая попытка проверяющего агента указать на оверинжиниринг отсекается фильтром анти-шума как «запрещенный совет по архитектурному рефакторингу». В результате в репозиторий коммитится паразитная надстройка, сжигающая контекст и токены во всех последующих сессиях.

## 2. Фундаментальный сдвиг: от «ошибок исполнения» к «архитектурному паразитизму»

Ревью-система должна различать два принципиально разных класса дефектов:

| Класс дефекта | Что проверяет | Как проявляется | Статус в v0.2.0 | Статус в v0.4.0 |
|---|---|---|---|---|
| **P1/P2 Functional & Security** | Нарушение логики, краевые случаи, уязвимости | Краш, утечка памяти, SQL-инъекция, битый контракт | Блокирует (PASS/BLOCK) | Блокирует (PASS/BLOCK) |
| **P2 Parasitic Architecture** | Изобретение велосипедов, мета-бюрократия, паразитный IPC | Раздувание токенов, параллельный транспорт, подмена продукта ритуалом | **Пропускается (PASS)** | **Блокирует (BLOCK)** |

## 3. Объективные критерии детекции паразитной архитектуры

Чтобы исключить вкусовщину и ложные срабатывания на качественный ООП/DDD-код, применяется **правило двух доказательств**. Кандидат становится дефектом **P2 correctness** только когда одновременно доказаны:

1. **Штатная альтернатива:** в репозитории или объявленном фреймворке уже есть доступный механизм для той же ответственности.
2. **Нулевая продуктовая дельта:** новый слой не добавляет пользовательской или доменной возможности и обслуживает только собственный процесс контроля.

Цена владения, новые границы процессов, рост хранилища и расход токенов доказывают impact, но не являются третьим условием. При отсутствии любого доказательства кандидат отклоняется или остается недоказанным.

### Матрица демаркации: Качественный дизайн против Паразитной надстройки

| Признак | Качественный ООП / DDD (РАЗРЕШЕНО) | Паразитная надстройка (БЛОКИРОВАТЬ) |
|---|---|---|
| **Отношение к фреймворку** | Расширяет штатные классы и порты для новой возможности. | Строит параллельный слой рядом с уже достаточным механизмом. |
| **Границы выполнения** | Внутрипроцессные вызовы методов, строгая типизация аргументов. | Выход в системный шелл, запуск подпроцессов ради одного вызова метода. |
| **Работа с состоянием** | Использует нативный Checkpointer / единую базу проекта. | Создает собственные JSON-файлы синхронизации (`human-inbox`). |
| **Безопасность** | Соответствует модели угроз окружения (локально vs публичный веб). | Избыточная криптография (Ed25519) для локальных флагов разработчика. |
| **Тестирование** | Проверяет вход/выход доменной логики (Given-When-Then). | Проверяет промежуточные файлы-квитанции о том, как запускались шаги. |
| **Наблюдаемость** | Структурированные события бизнес-домена и трассировка ошибок. | Тотальный дамп бинарного stdout/stderr системных команд в хранилище. |

## 4. Разбор 5 кейсов в терминах доказательной базы ревью

Ниже показано, как обновленный ревьюер обязан квалифицировать каждый из пяти прецедентов:

### Кейс 1: 41 CLI-скрипт вместо методов внутри существующих нод
- **Классификация:** `P2 — Parasitic Architecture: Subprocess Boundary Inflation`.
- **Доказательство Условия 1:** В проекте уже есть пайплайн (например, ноды графа в `src/workflows/nodes/`), выполняющиеся в едином рантайме.
- **Доказательство Условия 2:** Скрипты `admit-start-product`, `inspect-actions` и др. лишь вызывают сервисные функции, но требуют спавна нового процесса Node/Python, сериализации JSON через stdout и повторного парсинга конфигурации.
- **Impact:** Потери производительности на межпроцессное взаимодействие, потеря сквозного стектрейса при сбоях, раздувание кодовой базы на 41 точку отказа.

### Кейс 2: Самодельный PKI / Ed25519 Trust Store для флага «APPROVE»
- **Классификация:** `P2 — Parasitic Architecture: Cryptographic Overengineering`.
- **Доказательство Условия 1:** Проект выполняется локально на машине разработчика; граница доверия совпадает с границей доступа к файловой системе ОС.
- **Доказательство Условия 2:** Задача флага `APPROVE` — простая фиксация решения оператора (булево значение или enum в состоянии задачи).
- **Impact:** Введение асимметричных ключей, реестра доверенных лиц, механизма отзыва и base64url-подписей создает сложную инфраструктуру управления ключами, не добавляя реальной защиты от локального пользователя.

### Кейс 3: Протокол паузы через Exit Code 20 и файловый Inbox
- **Классификация:** `P2 — Parasitic Architecture: Shadow IPC and State Duplication`.
- **Доказательство Условия 1:** Используемый оркестратор (например, LangGraph) нативно поддерживает операцию `interrupt()` с сохранением снимка графа в постоянном хранилище и возобновлением по ID сессии.
- **Доказательство Условия 2:** Код возврата 20 и мониторинг папки `human-inbox` дублируют функционал прерывания и ожидания внешнего ввода.
- **Impact:** Файловый обмен подвержен гонкам при параллельных запусках, засоряет диск временными JSON-файлами и ломает штатные механизмы возобновления и визуализации графа.

### Кейс 4: Мета-пруфы каждого шага разработки (`ImplementationTaskProofBodyV1`)
- **Классификация:** `P2 — Parasitic Architecture: Self-Referential Process Verification`.
- **Доказательство Условия 1:** В проекте используется система контроля версий Git и штатный тест-раннер (`node:test` / `pytest`).
- **Доказательство Условия 2:** Сбор 28 промежуточных JSON-квитанций проверяет последовательность выполнения шагов генерации кода, а не работоспособность полученного модуля.
- **Impact:** Тесты проверяют структуру самих квитанций, создавая иллюзию 100% покрытия («все квитанции собраны»), в то время как продуктовый код остается непротестированным на реальных сценариях.

### Кейс 5: Враппер команд `capture-command` с сохранением вывода в ArtifactStore
- **Классификация:** `P2 — Parasitic Architecture: Telemetry Bloat`.
- **Доказательство Условия 1:** Логирование системных процессов уже обеспечивается стандартными потоками вывода ОС и логгером приложения.
- **Доказательство Условия 2:** Бинарный перехват каждого shell-вызова не несет бизнес-информации для логики приложения.
- **Impact:** Неконтролируемое раздувание постоянного хранилища дублирующимися логами, лишний слой перехвата потоков ввода-вывода, маскирующий реальные коды ошибок дочерних процессов.

## 5. Проектирование изменений в 4-стадийном конвейере

Топология остается прежней: четыре стадии, два параллельных hunter (`correctness` и `security`), без нового агента, lane, вызова модели или JSON-схемы стадии.

### Стадия 1: `review-context-scout`
Разведчик фиксирует доказанные штатные механизмы в существующих `invariants` и `relevant_consumers`, а неизвестные внешние контракты — в `unknowns`. Новое поле и широкое сканирование не вводятся.

### Стадия 2: `review-risk-hunter`
Только `lane: "correctness"` применяет правило двух доказательств. Кандидат остается `priority: "P2"` и `lane: "correctness"`; отдельный класс дефекта не вводится.

### Стадия 3: `review-finding-verifier`
Верификатор пытается опровергнуть оба доказательства и защищает оправданные Port/Adapter, Template Method, публичные CLI и криптографию для удаленной недоверенной стороны. Одного доказательства недостаточно для BLOCK.

### Стадия 4: `reviewer-kit`
Оркестратор синтезирует подтвержденный P2 correctness в существующий BLOCK и строгий конверт отказа.

## 6. Интеграция с контрактом отказа (`review-rejection-envelope@1`)

В архитектуре отказа (v0.4.0) зафиксирован формат JSON-конверта, передаваемого вызывающему агенту:
```json
{
  "schema": "review-rejection-envelope@1",
  "kind": "confirmed_findings",
  "diff_hash": "36d2455ab491f330bc2c670d08c8e16bafe6a0b8cf18a2b0cfcd512d015cb24c",
  "findings": [
    {
      "finding_id": "correctness-parasitic-1",
      "priority": "P2",
      "defect_class": "correctness",
      "file_path": "src/commands/advance.mjs",
      "line_start": 1,
      "line_end": 64,
      "verifier_argument": "The repository already exposes the same operation through its domain service, while this internal CLI adds no user-facing capability and only re-wraps that call.",
      "counterexample": "Call the existing in-process domain service; the added subprocess boundary only adds serialization and another failure point."
    }
  ]
}
```

Вызывающий агент получает четкий сигнал: **«Не строй параллельную инфраструктуру; используй методы доменных сервисов напрямую»**. Агент удаляет мусорные CLI и возвращается к продуктовому коду в своем обычном цикле.

## 8. Резюме

Представленный кейс доказывает: **опаснейший дефект ИИ-разработки — это не опечатка в переменной, а уход модели в строительство бесполезной бюрократической инфраструктуры вокруг кода**.

Интеграция протокола выявления паразитной архитектуры закрывает главную лазейку для сжигания токенов, заставляя агентов писать компактный, прямой и поддерживаемый продуктовый код, опирающийся на реальную архитектуру проекта.
